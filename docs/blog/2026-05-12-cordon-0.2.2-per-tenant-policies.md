# Cordon 0.2.2 — per-tenant policies, in three lines

Until today, integrating Cordon into a production agent left
operators with a difficult choice. The three default profiles
(`strict`, `default`, `permissive`) cover most cases — but the
*remaining* cases are exactly the ones that block adoption.

> *"`strict` blocks `rm -rf node_modules` in our CI image build.
> But `permissive` lets through `rm -rf /`. We need something in
> between, and we don't want to fork."*

That's three different design partners, in three different industries,
in the same week. So this release ships the in-between: a tiny text
DSL that takes `strict` as a base and carves out exactly the
exceptions your agents genuinely need.

## What the DSL looks like

```text
profile: strict

# Real-world carve-outs our CI image build needs:
allow when command_starts_with: "rm -rf node_modules"
allow when command_starts_with: "rm -rf ./build"

# Promote a known-risky pattern to a hard block:
block when path_starts_with: "/etc/" and kind: file

# Downgrade a noisy probe to flag-only:
flag when probe: typosquat
```

Three rule types — `allow`, `flag`, `block` — and six predicates:
`command_starts_with`, `command_contains`, `path_starts_with`,
`path_contains`, `probe`, `kind`. AND-joined within a rule, first
match wins.

That's the whole grammar. No nesting, no booleans, no regex. We
explicitly resisted the urge to ship "v1.0" of a policy language;
this is "v0.1 of a policy language that maps cleanly onto the
question customers actually ask."

## How you use it

In the SDK:

```python
from cordon import Action, Guard

guard = Guard.from_policy(open(".cordon-policy").read())
verdict = guard.check(Action(kind="shell", command="rm -rf node_modules"))
assert verdict.decision == "allow"   # carve-out fired
```

In Cordon Cloud (closed beta), the policy lives per-project on the
dashboard. The editor validates as you type, lets you "try this
policy" against a sample action without saving, and pushes updates
to every agent on your account in one round-trip. No code redeploy.

## Why this matters more than it looks

The interesting design constraint here was the **audit trail**.
When a security engineer reviews a `BLOCK` they don't recognise three
weeks later, they need to know whether it came from a probe (which
means we have a security finding) or a policy rule (which means
their operator carved it out, and there's a paper trail).

So the policy runtime *never* mutates the probe trail. The verdict
keeps the full list of probes that fired, in the order they fired.
The `decision` may change; the explanation gets a trailing
`; policy line 5 → allow when command_starts_with: 'rm -rf node_modules'`;
but the probe evidence stays exactly as the base profile produced it.

The dashboard rows show the rule annotation in the explanation column.
The audit report renders it as a clickable link back to the policy's
version history. The CLI's `--explain` mode prints the rule alongside
the probe evidence.

You can tell whether a verdict was "the strict profile chose to
allow this" or "the operator carved out an exception" without
opening a debugger. That's the bar; everything else follows.

## What else changed in 0.2.2

* `cordon.integrations.langchain.CordonGuardCallback` — for users
  whose agents are built via `langgraph.prebuilt.create_react_agent`
  or `langchain.agents.AgentExecutor` where the tool list isn't
  wrappable. Register one callback on the agent's `callbacks=` and
  every tool call gets guarded.

* The Cordon Cloud dashboard grew a Policies tab anchored at
  `#policies` — live validation, try-it panel, save/revert/delete.

* Postgres backend hardened: the storage layer now exposes
  `get_policy / put_policy / delete_policy` with monotonic version
  counters, and the same 5-test contract suite runs against both
  SQLite and Postgres in CI.

* GitHub Actions: matrix CI on Python 3.10 / 3.11 / 3.12, plus a
  tag-triggered release workflow that uses PyPI Trusted Publishing
  (OIDC). No API token to leak.

Total test count: 327 passing.
Total release size: a single `pip install --upgrade cordon-ai`.

## Try it

```bash
pip install --upgrade cordon-ai

cat > /tmp/policy <<'EOF'
profile: strict

allow when command_starts_with: "rm -rf node_modules"
allow when command_starts_with: "rm -rf ./build"
flag  when probe: typosquat
EOF

python -c '
from cordon import Action, Guard
guard = Guard.from_policy(open("/tmp/policy").read())
for cmd in ["rm -rf node_modules", "rm -rf --no-preserve-root /", "pip install requestz"]:
    print(f"  {guard.check(Action(kind=\"shell\", command=cmd)).decision.upper():<5}  {cmd}")
'
```

You should see `ALLOW`, `BLOCK`, `FLAG`.
